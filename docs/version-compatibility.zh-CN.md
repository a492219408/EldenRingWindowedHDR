# 游戏版本兼容性与运行时目标解析

分析日期：2026-08-31

实现文件：`src/game_compat.rs`

结论状态：App Ver. 1.16.2 与 1.17 已完成静态双版本审计；只有 1.17 完成了本 MOD 的真实游戏测试

## 为什么不再把完整 EXE 哈希当作唯一开关

旧实现只接受 App Ver. 1.17 的固定大小和 SHA-256，然后使用该版本的固定 RVA。这种方式的
优点是保守，但游戏只要更新一个无关函数，完整哈希就会变化，MOD 也会在所有相关 HDR
函数完全未变时失效。

另一方面，不能仅删除哈希判断并继续使用旧 RVA。对 1.16.2 与 1.17 的比较已经证明四个
目标并非按同一偏移整体移动：配置复制函数移动了 `-0x30`，后端实际状态函数移动了
`+0x1E00`，其他目标又使用不同偏移。所谓“给旧地址加一个版本差值”没有可靠依据。

当前方案因此把完整哈希改为“版本识别与额外交叉核对”，把是否允许 Hook 的最终决定交给
运行时结构解析。已知哈希仍有价值，但未知哈希不再自动等同于不兼容。

## 已审计的两个唯一二进制

备份目录中的“有 DLC”和“无 DLC”副本在各自版本内字节完全相同，因此四条路径实际只有
两个唯一 `eldenring.exe`：

| App Ver. | 文件版本 | 大小 | SHA-256 | 本 MOD 验证状态 |
| --- | --- | ---: | --- | --- |
| 1.16.2 | 2.6.2.0 | 86,998,096 | `34102B1C08BB5F769A724427A6F70FE29B3B732C31CF73693F861C48D3492DDB` | 静态解析通过，尚未实机运行本 MOD |
| 1.17 | 2.7.0.0 | 87,024,720 | `D1A84083C6C7C7902162FF098F7D86812839AA6B3575959398857E539C488134` | 静态解析通过，HDR/SDR 核心路径已实机验证 |

对应目标如下。函数名是按各版本映像基址 `0x140000000` 表示的 Ghidra 名称：

| 目标 | 1.16.2 RVA | 1.17 RVA | 双版本比较 |
| --- | ---: | ---: | --- |
| 公共 HDR 可用性 | `0x00952870` | `0x00953A10` | 控制流相同，RIP-relative 与 `call rel32` 位移不同 |
| HDR 行灰显谓词 | `0x00961A00` | `0x00962B30` | 逻辑相同，调用位移不同 |
| HDR 灰显谓词虚表 | `0x02B12248` | `0x02B152C8` | 相同 RTTI 类型与 6 项布局 |
| 图形配置复制 | `0x0025C7B0` | `0x0025C780` | 前 256 字节相同，包含 `source+0x15 → destination+0x1B` |
| 后端实际 HDR 查询 | `0x01E9D6D0` | `0x01E9F4D0` | 前 192 字节相同，仍经虚表 `+0x58` 查询独占全屏 |
| 安全 Cookie | `0x03C5ADB0` | `0x03C5EE10` | 由可用性函数的 RIP-relative 操作数动态求得 |

这说明 1.16.2 与 1.17 的相关 ABI、字段偏移和控制流均保持一致，但这里只能称为静态兼容
证据。1.16.2 尚未实际加载 DLL，也没有 HDR 显示器上的运行日志，不能把它写成“实机已支持”。

## 运行时解析的完整条件

解析器只扫描主模块 PE 头中带 `IMAGE_SCN_MEM_EXECUTE` 的节，并在读取每段内存前以
`VirtualQuery` 确认整段已提交、可读且没有 `PAGE_GUARD`。它不会扫描堆、其他 DLL、整个
进程地址空间或磁盘上的任意数据节。

必须一次性满足以下所有条件：

1. 公共 HDR 可用性函数的多段签名在全部可执行节中唯一命中。签名只忽略安全 Cookie 和
   四个相对调用的位移，栈布局、两个返回分支和其余控制流字节必须一致；
2. 扫描所有 `call rel32` 后，该函数必须恰有两个直接调用点；
3. 两个调用点中必须恰有一个符合“调用可用性函数并返回逻辑反值”的 19 字节灰显谓词；
4. 只从可执行节中的 RIP-relative `lea` 反向寻找虚表。候选虚表的第 3 项必须指向上一步
   谓词，其余 5 项必须都指向主模块可执行节；
5. 虚表前的 MSVC x64 Complete Object Locator 必须自洽，`pSelf` 必须回指自身，RTTI 名称
   必须是相同的 `std::_Func_impl<lambda_...>` 形状。编译器生成的 32 位十六进制 lambda
   哈希允许变化，但类型前后缀不能变化；
6. 图形配置复制签名必须唯一，并明确含有
   `movzx ..., [source+0x15] / mov [destination+0x1B], ...`，同时核对函数首部和尾部两个
   高偏移字段复制；
7. 后端实际 HDR 查询签名必须唯一，并明确包含能力位 `backend+0x32 bit 2` 和交换链虚表
   `+0x58` 调用；
8. 从公共可用性函数首条 RIP-relative 读取动态解析安全 Cookie；目标必须指针对齐，并落在
   主模块可读、非执行 PE 节；
9. 对已知哈希，所有动态结果还必须逐项等于上表记录的 RVA 和 6 个虚表项；任一差异都按
   内存冲突、分析错误或二进制异常处理。

解析得到的是一个不可拆分的 `GameTargets`。只有整组成功后，`game_hdr` 才会尝试安装内部
观察 Hook；每个安装点又会在写入前复核解析时捕获的函数首部、虚表邻项和 COL。默认
`windowed_hdr` 的公共可用性覆盖、后端实际状态覆盖与 PQ 所有权，仍要等所有前置 Hook 和
DXGI 工厂 Hook 都成功后才启用。

## 已知版本、未知版本与失败路径

### 已知版本

日志先显示 `recognized ...`，随后仍执行全部扫描，而不是直接使用表中地址。扫描结果必须与
已知表完全相符：

```text
COMPATIBILITY: recognized App Ver. ...; resolving all runtime targets instead of trusting fixed RVAs
COMPATIBILITY: all resolved RVAs and semantic checks match the known ... profile
COMPATIBILITY: target bundle resolved ...
```

### 未知版本

完整哈希未知时，解析器会尝试同一套严格条件。全部通过后允许功能继续，并写入显眼警告：

```text
COMPATIBILITY WARNING: unknown executable accepted because every signature, caller relationship,
RTTI/vtable check, security-cookie relocation, and unique-match requirement passed ...
```

这代表“相关二进制结构与已验证版本一致”，不代表该新版已经通过真实游戏、显卡驱动或显示器
测试。新版本首次运行仍应保留完整日志，并对 HDR 开启、关闭、持久化和 SDR 恢复做短回归。

### 解析失败或 Hook 冲突

0 个命中、多个命中、调用者数量变化、RTTI/虚表不一致、Cookie 指向异常、PE 节不可读或
已知版本结果偏离记录值，都会产生 `COMPATIBILITY FAILURE`。此时不会安装任何游戏内部 HDR
Hook，也不会请求 MOD 管理的 PQ 色彩空间。与版本无关的 DXGI/AGS 观察器仍可安装，以便日志
包含交换链、输出能力和导入状态；游戏按原生行为继续运行：

```text
COMPATIBILITY FAILURE: ...; refusing all internal HDR hooks and behavior changes
initialization completed in safe compatibility fallback ...
```

这种回退刻意优先“新版游戏可启动并留下诊断”，而不是让 initializer 因未知版本直接使整次
启动失败。若日志进入该路径，窗口态 HDR 不会由本 MOD 启用。

## 新游戏版本的维护流程

1. 保存新 `eldenring.exe` 的文件版本、大小和 SHA-256，不依据 App Ver. 字符串猜地址；
2. 首次只用 `mode = observe`，检查日志中的全部 `COMPATIBILITY` 行；
3. 若未知版本被结构解析接受，仍用 Ghidra 对四个目标、两个直接调用者、虚表 RTTI、字段
   `+0x15/+0x1B`、后端 `+0x30/+0x32` 和交换链虚表 `+0x58` 做人工复核；
4. 完成无边框 HDR 开→关、跨启动持久化、普通窗口化及 Windows HDR 关闭回退测试；
5. 只有静态和实机结果都成立后，才把新指纹加入 `KNOWN_BUILDS`，并更新 README 的验证状态；
6. 若解析失败，不应通过缩短签名、忽略多个命中或跳过 RTTI 来强行兼容。应先定位真实变更，
   必要时为新控制流增加独立、同样严格的解析分支。

## 当前证据边界

- **已确认：**同一实现中的所有签名、调用关系、RTTI/虚表和 Cookie 规则对 1.16.2、1.17
  两个真实磁盘 EXE 均唯一解析，结果与各自反编译地址一致；
- **已确认：**1.17 在当前 NVIDIA/HDR 环境中的窗口态 HDR、SDR 恢复和持久化；
- **待实机验证：**1.16.2 加载本兼容层后的运行行为；
- **设计上的尽力兼容：**未来未知哈希但相关机器码结构未变的版本；
- **不承诺：**控制流、字段布局、RTTI 或 DXGI 前提发生实质变化的新版本。此时必须安全失败，
  不能把“自动接受未知版本”解释成无限向前兼容。
